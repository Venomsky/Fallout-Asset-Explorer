# Fallout 2 PRO editor field model

The current standalone PRO workflow is an inspector, not an editor. `Fallout2PrototypeResolver.InspectStandaloneEntryAsync` decodes semantic fields only for Fallout 2 DAT2 entries and retains the complete bytes in `Fallout2StandalonePrototypeInspection.RawBytes`. Unsupported PID types, unsupported subtypes, incomplete records, and entries from other archive variants remain raw or partial. The UI can export a report or the original bytes as BIN; it cannot write a PRO record.

`Fallout2PrototypeEditorField` is a conservative Core model for future field-level editing work. It carries a field name and UI label, storage/value kind, numeric value when decoded, source offset and length only when known, a defensive copy of the original field bytes, optional bounds, editability classification, rationale, and evidence references. `FromDecodedField` always produces `ReadOnly`; the resolver is not changed to mark fields as edit candidates. `FromUninterpretedBytes` preserves opaque bytes without assigning an offset or meaning. The model does not serialize fields or edit records.

The resolver reads the first 32-bit big-endian value as the prototype PID. Its high byte selects the PID type and the low 24 bits are used as a one-based index into `proto/items/items.lst` for Item type 0 or `proto/scenery/scenery.lst` for Scenery type 2. The resolved entry is checked against the requested PID. Standalone selection bypasses list verification and labels that limitation. Other PID types are not semantically decoded.

The implemented field readers expose common Item and Scenery names plus subtype-specific fields. Existing offsets and widths are recorded in `Fallout2PrototypeField`; names such as `stairs.field_0`, `ladder.field_0`, `generic.field_0`, `field_34`, and `field_80` deliberately retain conservative identifiers where their complete meaning or value domain is unconfirmed. No numeric editing bounds are currently supplied by the editor model.

Resolver tests assert offsets, widths, and byte retention using synthetic prototype records. Those tests verify the implementation's current behavior, not compatibility with original game data. Before any field is classified as an editing candidate, its meaning, allowed values, cross-field constraints, version/subtype applicability, and byte-preserving round trip need stronger evidence. In particular, synthetic fixtures alone do not establish game compatibility.

## In-memory edit session

`Fallout2PrototypeEditSession` is an in-memory model only. It takes a snapshot of the supplied record bytes and copies its field definitions; callers cannot use it to modify the source array or the original field objects. It exposes original and current modeled numeric values separately, reports `IsDirty` by comparing them, and retains opaque/original bytes without writing them back. Field names are the session identities and must be unique. Known field ranges and decoded numeric values are checked against the source snapshot when the session is created; incomplete or mismatched source information is rejected.

`TrySetNumericValue` rejects unknown and read-only fields. Editing candidates are accepted only when they have a source range, numeric value kind currently supported by the model (`Int32BigEndian` or `UInt8`), nonempty rationale and evidence, and both minimum and maximum validation bounds. The proposed value must fit the representation and those bounds. A rejected operation does not change values or history. A same-value assignment succeeds without adding history. Undo and redo apply modeled values (not byte offsets), and a new edit after undo clears the redo branch. Returning all modeled values to their initial values clears `IsDirty`.

The current resolver-derived production fields remain `ReadOnly`; no production PRO field has been established as safe to edit. The successful edit-session fixtures use explicitly synthetic test fields and verify only the in-memory model's behavior. They do not confirm field semantics, ranges, or compatibility with Fallout 2 files. `Fallout2PrototypeRecordDraftBuilder` can create an in-memory copy of the source record with authorized numeric changes applied, but it does not serialize the complete PRO format, rewrite or export records, or establish byte-level round-trip or game-file compatibility.

## PRO Editor workspace

The `PRO Editor` workspace is populated from the standalone inspection of the currently selected `.PRO` entry in Archive Browser. It does not enumerate or index archive contents. The displayed source path, entry path, PID, type, subtype, inspection outcome, and read status come from `Fallout2StandalonePrototypeInspection`. Standalone selection is explicitly not verified through a MAP PID or prototype list.

The workspace displays only field metadata returned by the current inspection and represented by `Fallout2PrototypeEditorField`. Original and current values are shown separately; currently they are equal because the workspace exposes no field-editing controls and resolver-derived fields remain read-only. Offsets and lengths appear only when the field model supplies them. Unsupported or partial inspections retain their status and available raw bytes; a session snapshot is attached only when the entry was completely read, the subtype is supported, and the field metadata matches the original bytes. Raw-byte display is a bounded hex preview; omitted bytes remain available in the inspection model.

Undo and redo are disabled when the attached session has no recorded changes. The workspace has no PRO save, serialization, or export path and does not mark any production field as editable. The existing Archive Browser inspection remains available; the new tab is a separate presentation workspace over that selected-entry result, not a new resolver or source of format claims.

## Stage 37 — evidence audit

This audit separates what the project currently does from what external material supports. An offset asserted by `Fallout2PrototypeResolver` or a test is evidence of that implementation's behavior; it is not by itself evidence of the Fallout file format.

### External sources and provenance

1. 3. The PRO page links the older [Vault-Tec Labs/Fandom PRO format page](https://falloutmods.fandom.com/wiki/PRO_File_Format). That page returned HTTP 403 during this audit, so its contents were not used as evidence. Its relationship to the source-backed documentation could not be independently established.

The evidence sources have different scopes:

1. The pinned Fallout 2 CE revision is direct evidence of that implementation's in-memory layout, stream read/write behavior, and observed runtime call sites. It does not automatically establish original retail engine behavior or retail-file compatibility.
2. FODEV's PRO documentation derives from CE and is not an independent confirmation of CE behavior. The historical TeamX `pro_format.7z` is cited from a prior research report; it was not opened during this audit, so claims about its contents are reported evidence, not a source independently checked here.
3. Retail samples, list associations, and hashes below were supplied in user reports. They have not been independently inspected, recomputed, or verified unless a section explicitly says otherwise.
4. Conclusions drawn by comparing implementations, documentation, and reported samples are inferences; they are not direct observations of original binaries.

The Stage 37 source audit did not inspect local Fallout archives or individual records. No result in this document establishes byte-for-byte compatibility with retail Fallout 2 data.

### How to read the matrix

- **Confirmed externally**: the CE stream reader and writer agree on the serialized order and storage width, with matching field descriptions in the source-backed PRO documentation. Because that documentation derives from CE, this is one implementation lineage; it does not confirm retail data or other interpretations such as signedness and allowed values.
- **Partially confirmed**: layout has external support, but the meaning, allowed values, subtype behavior, or read/write agreement is incomplete.
- **Confirmed only in project code**: the claim describes FAE's parser/test behavior; available support is limited to project code or fixtures without attributed game-record provenance.
- **Unconfirmed**: the available evidence does not establish the field's meaning or a safe interpretation.

### Project tests and evidence classification

- `Fallout2PrototypeResolverTests.ResolveAsync_DecodesConfirmedItemFieldsAtExactOffsetsAsBigEndian` creates records with `CreateItemPrototype`, which allocates a byte array and writes only PID/subtype before the test writes synthetic values. The word “Confirmed” in the test name does not mean confirmed against the game.
- `ResolveAsync_DecodesSceneryCommonFieldsAtExactOffsetsAsBigEndian` and `ResolveAsync_DecodesScenerySubtypeWordsAtVerifiedOffsets` likewise use generated byte arrays and test the resolver's behavior, not retail files.
- `ResolveAsync_DecodesObservedGenericSceneryByteAndRawWordAtExactOffsets` uses a hard-coded hex string but records no archive, file path, provenance, or independent expected-data source. It is not treated as a known game sample.
- `ResolveAsync_MapsOnlyConfirmedSceneryMaterialBoundaries` exercises synthetic values `0` and `7`; it does not test all values or prove game semantics.
- `Fallout2PrototypeEditorFieldTests` uses synthetic source bytes and explicitly `SyntheticData` evidence. `Fallout2PrototypeEditSessionTests` tests model behavior using synthetic candidate fields only. Neither test suite establishes PRO compatibility or promotes a production field to editable.
- `Fallout2PrototypeEditorField.FromDecodedField` classifies resolver-derived fields as `ReadOnly`; `ProEditorViewModel` marks resolver metadata `Unverified`. No production field has independently verified editing bounds.

Thus the project tests **confirm only FAE behavior**. ## Future design proposal — trusted field-definition registry

**Stage 44 status: registry/session integration implemented; production registry remains empty.** The schema, evidence, definition, inspection-context, approval-capability, and registry types are in `src/FalloutAssetExplorer.Core/Fallout2PrototypeFieldDefinitionRegistry.cs`. This section still describes future field approvals and serialization. The integration adds no format claims, approves no current field, does not resolve the Weapon damage order, and does not change production field editability.

`Fallout2PrototypeFieldDefinitionRegistry.Production` is immutable and empty. Its public resolution method is default-deny and requires an exact schema and field match, matching representation, offset, width and numeric bounds, in-record bounds, original bytes, and decoded value. Reviewed-registry construction is internal, rejects non-independent evidence statuses and duplicate schema/field identities, and is not exposed to arbitrary callers. Evidence metadata remains an audit trail, not proof by itself; internal registration still requires source review. The registry records a provenance-group label but does not establish source independence from that label; reviewers must inspect source lineage, and a status enum or distinct label is not proof. A test-only internal factory is available to the friend test assembly and does not populate the production registry.

The public session constructor has been removed. `Fallout2PrototypeEditSession.CreateProduction` binds a session to the inspection context, registry and original bytes; before each edit, Undo or Redo, the session resolves the field again and requires a matching registry definition in addition to the field being an `EditingCandidate` with valid numeric bounds. Caller-created fields or approval metadata cannot substitute for that resolution. Synthetic mechanics use the internal `CreateForTests` path, available to the friend test assembly only. `ProEditorViewModel` uses the empty production registry and continues to create production fields as read-only. The current inspection model has no reliable game-build/version field, so no version range is invented.

### Proposed definition and evidence model

Keep the current `Fallout2PrototypeEditorField` as an inspection/presentation model. Its `Editability`, rationale, evidence list, offsets, and value bounds are descriptive metadata; none of them alone should authorize mutation. In particular, `EditingCandidate`, a nonempty note, an evidence enum, or a syntactically valid byte range is not proof that a field is correctly understood.

A reviewed registry entry would bind a field rule to its exact applicability:

```text
PrototypeSchemaKey:
    Game, Format, PID type, subtype, applicable game/build scope

PrototypeFieldRule:
    stable field ID, schema key, field name,
    value kind/encoding, serialized offset and width,
    approved validation rule, evidence claims

EvidenceClaim:
    source URI or repository path, exact source version/commit,
    source location, claim supported, applicability,
    provenance/lineage group, evidence kind,
    conclusion status and limitations
```

Evidence kind and conclusion status should remain separate. For example, a synthetic test can confirm a model's behavior, but its claim status is `SyntheticOnly`; project code can establish what FAE decodes, but not independently verify the game format; a hypothesis or unresolved claim cannot qualify as an approval basis. Record source lineage so two documents derived from the same implementation are not counted as independent corroboration. A confidence label may summarize the reviewed evidence, but must not itself grant edit permission.

Any future production entries must be explicitly reviewed. Resolution is a default-deny operation keyed by the complete schema and field identity:

```text
TryResolveApprovedRule(schemaKey, fieldId) -> ApprovedFieldRule or no rule
```

`Fallout2ApprovedPrototypeField` can be constructed only inside Core and is not accepted as caller-supplied session input. The production session resolves the rule against its inspection's Game, Format, PID type, subtype, field ID, offset, width, representation, numeric bounds and original bytes before accepting an edit. It repeats resolution before each mutation and history operation. Evidence display remains useful to users, but it is not the authorization mechanism.

### Approval criteria and session boundary

Before a production rule can enter the registry, reviewers should establish all properties needed for the proposed edit: field identity and subtype applicability; serialized location, width, and representation; any editable values and cross-field constraints; and behavior of unchanged bytes. Evidence must directly support each property, with provenance and independence assessed. A rule with an unresolved order, conflicting sources, undocumented value bounds, or only synthetic/project-code evidence remains absent from the production registry.

The resolver and standalone inspection remain read-only. The PRO workspace creates its in-memory session with the empty production registry, so decoded fields remain inspection-only. Unsupported, partial, mismatched, or unverified inspections receive no approval and cannot be edited. The registry must match the exact subtype and any applicable version scope; it must not infer authorization from a PID, an archive path, or a field name alone.

Existing synthetic session tests use the internal `CreateForTests` path, isolated from the production registry. Synthetic fixture definitions can be used only by the friend test assembly and are rejected by reviewed-registry creation. They must never be loaded into or interpreted as production approval entries.

### In-memory record draft and future serialization

`Fallout2PrototypeRecordDraftBuilder.Build` accepts the inspection context and its production edit session. It rejects a context that is not the exact snapshot bound to the session, revalidates every changed field through the session and its registry, and writes only `Int32BigEndian` and `UInt8` values into a fresh byte-array copy. The builder holds the edit-session lock through snapshot validation and patch assembly, so its fields come from one stable session state relative to concurrent edits. The `Int32BigEndian` encoding is explicitly big-endian. Bytes outside changed fields remain copied verbatim. Before applying any values, the builder rejects overlapping ranges among changed, authorized fields; a rejected draft exposes no partial byte output. This API creates only an in-memory field patch and is not a full PRO serializer or disk-save path.

Future serialization still requires schema-wide definition review and a complete serialization plan. Validate ranges when registering definitions for the same schema, then validate the complete resolved write plan again immediately before serialization. Use checked half-open ranges `[offset, offset + length)` and reject unknown, out-of-record, or overlapping writable ranges by default. Adjacent ranges are not overlapping. Permit overlap only if a future format rule explicitly defines an alias and supplies a single unambiguous encoding/consistency rule; do not infer aliases from matching names or values. Preserve unknown bytes verbatim and never include them in a write plan without a separately approved rule.

Tests for the draft builder cover no-op and changed drafts, disjoint and overlapping ranges, snapshot and field consistency, supported numeric encodings, preservation of untouched bytes, defensive copies, and Undo/Redo rebuilds. Future serializer tests must additionally cover complete schema plans, adjacent ranges, arithmetic overflow, and any explicitly approved alias behavior. No test here establishes compatibility with retail PRO files.

### Migration and required tests

The session boundary is integrated, but field approval remains pending: retain decoded production fields as `ReadOnly`; keep the registry empty until exact field evidence is reviewed; do not promote current `EditingCandidate` metadata or synthetic test fixtures automatically. The unresolved Weapon `minDamage`/`maxDamage` mapping and other disputed fields remain unregistered until independently resolved.

The registry, session, draft builder and PRO Editor test schema/range/source matching, default denial, rejected synthetic evidence, authorization rejection without state/history changes, synthetic-only session mechanics, preservation of read-only production fields, and no-partial-output behavior for overlapping draft ranges. Before registering real production definitions, add data-backed tests for evidence provenance and each approved field's full value rules. A complete serializer will require its own format-level plan and tests.
